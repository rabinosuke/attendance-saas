# 勤怠管理SaaSのコーディング規約

制定日：2026年11月14日

最終更新日：2026年11月15日

画面用の `frontend` とAPI用の `backend` に共通で適用する。このプロジェクトで新しく書くコードや修正するコードは、以下にそろえる。実装の名前は英語、説明とコメントは日本語を基本とする。

## 名前の付け方

| 対象 | 規約 | 例 |
| --- | --- | --- |
| 変数・引数・プロパティ | 小文字から始め、単語の区切りを大文字にするcamelCase | `attendancePool`、`companyId` |
| 関数・メソッド | camelCaseで、何をするか分かる名前にする | `getEmployee`、`createCompany` |
| 型・インターフェイス・クラス | 各単語を大文字から始めるPascalCase | `Employee`、`LoginRequest`、`Pool` |
| Reactコンポーネント | PascalCase | `LoginForm`、`AttendanceTable` |
| 真偽値 | 状態が読み取れる名前にする | `isActive`、`hasPermission` |

意味のない省略や、見分けにくい名前を避ける。`db`、`id` など意味が定着している略語は使ってよい。DBの物理名とTypeScript側の名前は、既存のスキーマ定義に合わせる。

## 書式と変数宣言

- インデントは半角スペース2個にする。
- 通常の文字列はダブルクオートで囲む。変数を埋め込むテンプレート文字列はバッククオートを使う。
- 文末にセミコロンを付ける。
- 変数宣言は基本を `const` とし、再代入が必要なときだけ `let` を使う。`var` は使わない。
- `if` などの処理本体は、1行でも波括弧で囲む。

## 型の扱い

- `tsconfig.json` の `strict: true` を維持する。
- 明らかに型を推論できる変数へは、同じ型を重ねて書く必要はない。
- 関数の引数やAPIの入出力は、必要なデータの形が分かる型を付ける。
- 型チェックを回避するために `any` を安易に使わない。外部入力は実行時にも内容を検証する。
- `as` による型の指定だけでは、実際の値は検証されない。型エラーを消すためだけに使わない。

## 画面とAPI通信の役割分担

画面の表示・操作と、API通信の実装を分ける。APIの呼び出し方を変更するときに、画面の見た目や操作のコードを追わずに修正できるようにする。

| 担当 | 置く処理 | 配置 |
| --- | --- | --- |
| 画面・操作 | 入力値の取得、送信イベント、送信中・エラーの状態管理、表示条件、画面遷移 | `frontend` の画面・コンポーネント |
| API通信 | URL・HTTPメソッド・ヘッダーの指定、JSON化、送受信、応答の読み取り・形式確認 | `frontend/lib/api/` の通信専用ファイル |
| サーバー処理 | 社員検索、パスワード照合、認証・認可、業務処理、DB操作 | `backend` のAPIと共通処理 |

- 画面ファイルにはAPIを呼ぶ操作の流れを書き、`fetch`による通信の実装は通信専用ファイルへ置く。
- 通信専用ファイルは機能ごとにまとめる。ログインなどの認証関連は `frontend/lib/api/auth.ts` に置く。
- 通信関数にはフォーム要素を渡さず、画面側で取り出した入力値を渡す。入力・戻り値の型と、外部から届いた値の検証は「型の扱い」に従う。
- 通信関数の中では、Reactの状態変更、画面遷移、DOMの読み書きを行わない。呼び出し元が結果を受け取り、表示や操作へ反映する。
- エラーの有無やボタン文言を切り替える程度の短い表示条件は、JSXに記述してよい。
- 関連する状態と操作が複雑になったり、複数の画面で同じ処理を使ったりするときは、カスタムフックへまとめる。カスタムフックは、Reactの状態と操作をまとめて切り出す関数を指す。
- 表示部品や処理は、役割が分かれたとき、再利用するとき、読みづらくなったときに分割する。最初からすべての要素を別ファイルにしたり、不要な共通化や階層を追加したりしない。

## コメントと説明

コメントには、処理の目的や、その方法を選んだ理由を書く。細かい処理・条件・制約についても、日本語で意味を補足する。

- テーブルの列には、保存する値の意味、NULLや初期値の意味を補足する。
- 外部キーには、どのテーブルのどの列との対応を守るかを書く。会社IDと社員IDなど、複数列を組み合わせる理由も説明する。
- 一意制約・CHECKには、重複を禁止する単位や、拒否するデータの条件と理由を書く。
- 索引には、どの検索で使うことを想定しているかを書く。
- セッション処理には、有効期限の比較、利用時の更新、ログアウト時の無効化、期限切れデータの削除について、実装した条件と目的を補足する。未実装の処理を、既に行われるものとしてコメントに書かない。

学習用の詳しい説明はチャットや資料でも補足し、実装の変数名や関数名は英語にする。

## フレームワークと生成ファイル

- ライブラリが指定する `client`、`schema`、`max` などの名前は変更しない。
- Next.jsが指定する `page.tsx`、`route.ts` などのファイル名は、その規則に従う。
- 型定義やマイグレーションなどの生成ファイルは、生成元と整合する方法で管理する。適用済みマイグレーションを書き換えず、新しいものを追加する。

## 確認方法

以下はリポジトリのルートから実行する。型チェックとESLintは役割が異なるため、変更した側のチェックを行う。

フロントのESLint：

```bash
docker compose run --rm --no-deps frontend npm run lint
```

フロントの型チェック：

```bash
docker compose run --rm --no-deps frontend npx tsc --noEmit --incremental false
```

バックエンドの型チェック：

```bash
docker compose run --rm --no-deps backend npx tsc --noEmit --incremental false
```

### 自動チェックの設定状況

2026年11月14日時点では、フロントにNext.js・React・TypeScript用のESLint設定がある。バックエンドはESLintのパッケージを導入済みだが、設定ファイルと実行用スクリプトはまだない。

Prettierは両方とも未導入。この規約を書くだけで自動整形が有効になるわけではないため、書式は現時点では手動でそろえる。型チェックや既存のESLintだけで、ここに書いた命名・書式のすべてが自動検査されるわけではない。

画面とAPI通信の役割分担は、現在はレビューで確認する。ファイル間の依存関係を制限するESLintルールは未導入。
